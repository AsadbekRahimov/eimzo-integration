# E-IMZO usage examples

This module includes browser examples for the three common integration flows:

- `/eimzo/examples/login`
- `/eimzo/examples/document-sign`
- `/eimzo/examples/action-sign`

The examples use the same `EimzoBridge` JavaScript wrapper and the same backend endpoints that an application can call from its own UI.

## 1. Login with E-IMZO

Use login when you only need to prove that the current browser user owns an E-IMZO certificate.

Flow:

1. Browser requests `GET /eimzo/auth/challenge`.
2. Backend gets a short-lived challenge from E-IMZO-SERVER and stores it in `eimzo_challenges`.
3. Browser signs that challenge with `create_pkcs7`.
4. Browser posts `{ challenge, pkcs7 }` to `POST /eimzo/auth/verify`.
5. Backend verifies the PKCS#7 through E-IMZO-SERVER, stores certificate/signature data, and logs the matching user in.

For login, the signed document is the challenge string. A file is not required.

Database records:

```text
eimzo_challenges
- challenge
- purpose = auth
- ip
- user_agent
- meta.server_payload
- expires_at
- used_at

eimzo_certificates
- serial_number
- cn
- tin
- pinfl
- subject_dn
- issuer_dn
- valid_from
- valid_to
- last_verify_payload
- last_verified_at

eimzo_signatures
- user_id
- certificate_id
- document_type = auth-challenge
- document_name = challenge:{challenge}
- document_size
- document_hash = sha256(challenge)
- pkcs7
- verification_status
- verification_payload
- verified_at
```

User lookup is controlled by:

```env
EIMZO_USER_MODEL=App\Models\User
EIMZO_USER_LOOKUP_COLUMN=tin
EIMZO_AUTO_REGISTER=false
```

## 2. Document signing

Use document signing when the user must sign a contract, invoice, act, XML, JSON, or any business document.

In E-IMZO documentation, `Document` means the bytes being signed. It does not have to be a PDF. The browser base64 encodes the data and passes it to `create_pkcs7`.

Typical browser payload:

```json
{
  "document_type": "contract",
  "document_name": "contract-2026-001.json",
  "data": "{ original document content }",
  "detached": false,
  "attach_timestamp": true
}
```

Attached vs detached:

- `detached=false`: PKCS#7 contains the original document. This is easier to archive and verify later.
- `detached=true`: PKCS#7 contains only the signature. You must store the original document separately and pass it again during verification.

Database records in `eimzo_signatures`:

```text
user_id
certificate_id
document_type
document_name
document_size
document_hash
pkcs7
pkcs7_path
detached
pkcs7_with_timestamp
signed_at
timestamp_at
verification_status
verification_payload
verified_at
meta
signable_type
signable_id
```

Recommended application storage:

- Store your actual document in its own table or storage disk.
- Store `document_hash` on both your business record and the E-IMZO signature.
- Store `signature_id` or use `signable_type` / `signable_id` to link the signature to the document.
- Keep `pkcs7_with_timestamp` when timestamping is enabled.

## 3. CRM action signing

Use action signing when the user is not signing a file, but confirming an operation:

- approve invoice
- reject application
- cancel contract
- publish tender
- confirm payment

The signed document should be canonical JSON generated by the backend.

Example canonical JSON:

```json
{
  "action": "approve_invoice",
  "amount": 1500000,
  "approved_by": 1,
  "currency": "UZS",
  "entity_id": 1024,
  "entity_type": "invoice",
  "issued_at": "2026-05-03T19:20:00+05:00",
  "nonce": "example-nonce-123"
}
```

Canonical means:

- stable field names;
- stable field order;
- backend generated;
- includes entity id/type;
- includes amount/status or other important values;
- includes timestamp and nonce;
- user cannot silently change it in the browser.

Recommended business table:

```text
signed_actions
- id
- user_id
- action
- entity_type
- entity_id
- payload_json
- payload_hash
- signature_id
- certificate_id
- signed_at
- ip
- user_agent
```

The E-IMZO module stores the cryptographic envelope in `eimzo_signatures`. Your CRM table stores what the signature means for your business process.

## Verification rule

Never treat a PKCS#7 as valid only because the browser returned it. Always verify on the backend:

1. Verify PKCS#7 through E-IMZO-SERVER.
2. Check `verification_status = valid`.
3. Check certificate fields match the expected user or organization.
4. Check the signed document hash matches the business record.
5. For CRM actions, check the canonical JSON still matches the operation being applied.
